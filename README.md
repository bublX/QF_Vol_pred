# QF_Vol_pred

Прогнозирование дневной реализованной волатильности (σ = √RV) акций MOEX.
Цель — волатильность следующего наблюдаемого дня. RV — сумма квадратов
внутридневных логарифмических доходностей в процентах; σ — корень из RV.

## Установка и запуск

### Требования

- [uv](https://docs.astral.sh/uv/) — менеджер пакетов и окружений (обязателен).
  Python 3.14 uv скачает сам.
- OpenMP — нужен XGBoost и LightGBM.

| ОС      | uv                                                                                                | OpenMP                                                                                                                                                      |
|---------|---------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------|
| macOS   | `brew install uv`                                                                                 | `brew install libomp`                                                                                                                                       |
| Linux   | `curl -LsSf https://astral.sh/uv/install.sh \| sh`                                                | обычно уже есть; если нет: `sudo apt install libgomp1` (Debian/Ubuntu) или `sudo dnf install libgomp` (Fedora)                                              |
| Windows | PowerShell: `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 \| iex"` | входит в [Microsoft Visual C++ Redistributable](https://learn.microsoft.com/cpp/windows/latest-supported-vc-redist) (`vcomp140.dll`); обычно уже установлен |

### Установка

```bash
uv sync --locked
```

### Проверка

```bash
uv run pytest           # тесты
uv run ruff check .     # линтер
uv run ruff format .    # форматирование
```

### Запуск

Все команды запускаются из корня проекта.

Комплектный архив минутных цен хранится в `data/archives/1m_2014_2025/`.
Этап `prepare` распаковывает нужный CSV и проверяет его структуру; если CSV уже
существует, он проверяется и используется повторно. Повторное скачивание не требуется.
Описание исходника и ручная распаковка — в [инструкции по данным](data/README.md).

В командах замените `<experiment>` именем выбранного YAML-файла из `configs/`.
Имена файлов и параметры экспериментов могут меняться; общие значения
наследуются из `configs/default.yaml`.

```bash
uv run python main.py --config "configs/<experiment>.yaml" --stage prepare  # -> data.raw_dir / data.raw_file
uv run python main.py --config "configs/<experiment>.yaml" --stage process  # -> processing.processed_dir
uv run python main.py --config "configs/<experiment>.yaml"                  # stage train -> output.reports_dir / <output.name>_results.csv
```

Для скачивания другого набора настройте секцию `data` и выполните `--stage load`.
Параметр `data.source_interval` передаётся бирже как код интервала свечей MOEX ISS;
выбирайте поддерживаемый биржей интервал. Произвольные минутные интервалы
формируются локально на этапе `process`.
Этап `process` выполняется для каждого варианта обработки; затем его данные могут использовать разные модели.
Обучение по умолчанию не запускает `prepare`, `load` или `process` автоматически.

Все значения по умолчанию лежат в `configs/default.yaml`.
Файл эксперимента переопределяет только то, что отличается:
вложенные словари объединяются, списки заменяются целиком.
Новый эксперимент — новый YAML-файл в `configs/` с обязательным `model.name`
(`har`, `rf`, `xgb` или `lgbm`). Для HAR выберите `features.feature_set: har`.
Для HAR и RF задайте `split.use_validation: false`, `split.valid_end: null`
и границу обучения `split.train_end`; для XGBoost и LightGBM можно использовать
стандартную схему с валидацией и refit.
Поле `output.name` задаёт имя результата; если оно не задано, используется имя модели.
Новая модель — класс в `source/models/` и строка в `MODELS` в `source/models/registry.py`.

## Настройка обработки данных

Исходный архив содержит минутные цены закрытия, без остальных полей OHLCV.
`data.source_interval` обозначает длительность исходных свечей в минутах при
агрегации, `data.interval` — длительность итоговых баров. Для комплектных минуток
оставьте `source_interval: 1` и выберите, например, `interval: 3`, `5` или `15`.
Итоговый интервал должен быть не меньше исходного и кратен ему.

В `processing` задаются границы сессии `session_start` и `session_end` в формате
`HH:MM`: начало включается, конец не включается. Учитываются будние дни.
Бары отсчитываются от начала сессии; последний неполный бар отбрасывается.
Ценой бара становится последнее непустое значение `close` каждого тикера.
Стандартные границы сессии заданы в `configs/default.yaml`; эксперимент может
переопределить их. Для сравнения интервалов явно согласуйте границы сессии,
доли покрытия и фильтры. Одинаковое окно в барах охватывает разное время
при разных длительностях бара.

Параметры покрытия решают разные задачи:

- `min_bar_coverage` — минимальная доля исходных свечей внутри итогового бара,
  от 0 до 1. Даже при 0 нужна хотя бы одна свеча; иначе цена бара остаётся `NaN`.
- `min_day_coverage` — минимальная доля итоговых баров с реальной ценой за день,
  от 0 до 1, исключая 0. Порог считается до заполнения пропусков:
  `max(2, ceil(expected_bars_per_day * min_day_coverage))`.

После агрегации каждый тикер проходит последовательность:

```text
Подготовка и сортировка → проверка покрытия дня → price_steps → returns → steps → удаление строк без close или returns → RV
```

| Поле в `processing` | Назначение | Доступные имена |
|---|---|---|
| `price_steps` | Список шагов обработки цен до расчёта доходностей | `hampel`, `forward_fill` |
| `returns` | Обязательное описание расчёта доходностей | `log_returns` |
| `steps` | Список шагов обработки рассчитанных доходностей | `hampel`, `clip` |

Шаги каждого списка выполняются в указанном порядке. Настройки обработки
из `configs/default.yaml`:

```yaml
processing:
  price_steps:
    - name: hampel
      params: {column: close, window_size: 5}
    - name: forward_fill
      params: {}
  returns:
    name: log_returns
    params: {}
  steps:
    - name: hampel
      params: {window_size: 5, sigma: 3.0, const: 1.4826}
    - name: clip
      params: {max_return: 5}
```

По умолчанию Хампель применяется дважды: к `close` до заполнения пропусков
и к `returns` после расчёта доходностей. `column` выбирает фильтруемый столбец;
если он не указан, используется `returns`. `window_size` — полуширина окна:
значение 5 означает до 11 наблюдений. Окна Хампеля не пересекают границы дней.

`forward_fill` заполняет цены только внутри дня и удаляет начальные пропуски
до первой известной цены. `log_returns` считает `100 * log(close / previous_close)`
внутри каждого дня; первое наблюдение получает `NaN`, ночной разрыв не учитывается.
`clip` ограничивает доходности значениями ±`max_return` в процентных пунктах.

Чтобы отключить дополнительные шаги в эксперименте, задайте пустые списки:

```yaml
processing:
  price_steps: []
  steps: []
```

При этом сохраняются проверка покрытия дня, расчёт доходностей и завершающее
удаление строк без цены или доходности. Для замены фильтра укажите новый список
целиком; для отключения только Хампеля на ценах оставьте в `price_steps` один
`forward_fill`.

Результаты сохраняются в `processing.processed_dir`: `RV/`, `rv_matrix.csv`,
`profit_matrix.csv` и `missing_days.csv`. Конфиги с одинаковым каталогом используют
одни обработанные данные; повторный `process` перезаписывает результаты.
Для сравнения вариантов задавайте разные `processed_dir` и `output.name`.
После изменения интервала, сессии или шагов обработки выполните `process`, затем `train`.

### Запуск нескольких моделей

Если несколько конфигов используют одинаковые исходные данные, интервал,
границы сессии и все параметры обработки, выполните `process` один раз
с любым из них. Затем запускайте обучение с каждым конфигом отдельно.
Все эти конфиги должны указывать один `processing.processed_dir`,
а для разных результатов следует задать разные `output.name`.

При сравнении двух интервалов подготовьте отдельный каталог данных для каждого,
выполните две обработки и обучите модели на соответствующих наборах. Обучение
читает готовый CSV и не сверяет его происхождение с текущими параметрами конфига,
поэтому после изменения обработки нужно заново выполнить `process`.

### Добавление обработчика

1. Создайте класс-наследник `ProcessingStep` в `source/data_processors/steps/`
   с методом `transform(self, data, ticker="")`. На вход поступает таблица одного
   тикера с `date` типа datetime и данными соответствующей стадии. Возвращайте
   преобразованную таблицу, сохраняя исходную неизменной.
2. Зарегистрируйте класс в `steps/registry.py`: в `PRICE_STEPS` для цен,
   `STEPS` для доходностей или `RETURN_CALCULATORS` для их расчёта.
3. Выберите зарегистрированное имя в YAML и передайте аргументы конструктора
   через `params`. Порядок шагов задаётся списком, код `DataProcessor` менять не нужно.
